국가별 히트펌프·HVAC 유튜버에게 전용 할인코드를 주고, 그 코드로 유료 전환한

현재 병목이 유입량(검색 클릭 28일 34회)이므로 "성과가 날 때만 비용" 구조가 맞다.

## 3. 시스템 설계

### 3.1 원칙
- **파트너 회계는 접근 권한과 완전히 분리.** 웹훅의 기존 역할(구독 창 연장)은 건드리지 않고,
  파트너 처리는 별도 try/catch — 실패해도 회원 접근에 영향 0 (fail-open 원칙 유지).
- **모든 금액은 원장(ledger)의 합.** 보고서·잔액은 원장에서 계산만 한다 (직접 수정 금지).
- **개인정보:** 파트너 보고서에는 **집계 숫자만** — 가입자 이메일·이름·회사명 절대 미포함.
  개인정보 처리방침에 "제휴 코드 실적 집계" 항목 추가.
- **송금은 사람이 한다.** 시스템은 계산·통보·기록만. 돈을 움직이는 자동화 없음.

### 3.2a 파트너 링크 캡처 (선행 수정)
`src/services/signupRef.ts`는 허용 목록(`KNOWN`)에 없는 ref를 전부 `'other'`로 저장한다 —
지금 상태로는 `?ref=p-<slug>` 링크 귀속이 사라진다. 1단계에서 `p-[a-z0-9-]{1,20}` 패턴을
그대로 저장하도록 확장 (파트너 slug는 admin 등록 시 이 규칙으로 발급).

### 3.3 웹훅 확장 (`google_cloud_function_billing/index.js`)
1. `transaction.completed` → 기존 처리 후 `recordPartnerCommission(txn)`:
   - 첫 결제: `txn.discount_id`가 `partnerCodes`에 있으면 귀속 생성 (없으면 회원의 `signupRef`가 파트너 slug인지 확인).
   - 귀속된 구독이면, `commissionEndsAt` 이내일 때 원장에 `commission` = `round(payout_totals.earnings × rate)`.
   - `earnings`가 null이면 `pending` 표시 → 마감 작업이 Paddle API로 재조회.
2. `adjustment.*` (refund·chargeback, 승인된 것) → 해당 거래의 커미션 비율만큼 `clawback` (음수).
3. 귀속 생성 시점에 셀프 추천 검사 (파트너 이메일 = 가입자 이메일 등) → 의심 건은 admin 검토 대기.

### 3.4 월 마감 작업

- 오너가 admin에서 검토 → **승인 → 발송**. (승인 없이 자동 발송 안 함)

## 5. 리스크 체크리스트
- [ ] 파트너 처리 실패가 회원 접근에 영향 주지 않음 (별도 try/catch, 테스트)
- [ ] 보고서·CSV에 개인 식별 정보 없음
- [ ] 원장 멱등성 (웹훅 재전송·수동 재실행 시 중복 커미션 0)
- [ ] 송금 수수료·환율은 실비로 기록
- [ ] 계약서: 광고 표시 의무, 코드 정지권, 셀프 추천 금지, 잔액 처리, 종료 조건, 준거법
- [ ] 마케팅 링크는 `?ref=` 필수 규칙 유지 (파트너 링크 `?ref=p-<slug>`)
